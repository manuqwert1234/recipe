recipes

Drive websites through their accessibility tree instead of screenshots and pixel guessing. Real logged-in Chrome, auditable JSON recipes, in-page replay — built for AI agents and humans alike.

Vision-based browser agents look at a screenshot, guess a pixel coordinate, and click — which "succeeds" whether or not it hit the right thing. recipes reads the page's real accessibility tree instead, so every action either resolves against a labeled element or raises a typed error. Cheaper, faster, and failures are visible instead of silent.

No vision, no guessing

A page becomes a list of labeled elements — e5: button "Search". Actions target the element, not an (x, y) that may or may not still be there.

Real Chrome, real session

Runs against your actual, logged-in Chrome — a dedicated profile, not your default one. Sites you're already signed into just work.

Read before it runs

A repeatable flow is a plain JSON file with explicit assertions. Review it before it ever touches a real account.

Fails loud

A wrong assertion stops the run and says exactly what didn't match — it never reports success it didn't actually get.

Requires Node 18+ and Google Chrome. macOS only for now — Linux/Windows Chrome paths exist in the code but are unverified.

Quickstart

No separate setup step — the first command starts Chrome automatically if it isn't already running.

recipes open https://example.com --session s    // log in here if the site needs it
recipes snapshot --session s --interactive      // see what's on the page, by label not pixel
recipes click e5 --session s
recipes fill e9 "hello" --session s

For a flow you'll repeat:

recipes record capture.json --session s --duration 15000
recipes recipe from-network capture.json my-flow.json --site example.com
recipes recipe show my-flow.json     // read exactly what it will do, first
recipes recipe run my-flow.json --session s

How it works

No server process of ours runs continuously. The only long-lived thing is Chrome itself — every CLI invocation is a fresh, short-lived process that reconnects to it.

Snapshots & refs

recipes snapshot reads the page's accessibility tree and returns a flat list of labeled elements, each with a short ref like e12:

$ recipes snapshot --session s --interactive
[e1] link "Home"
[e2] textbox "Search"
[e3] button "Submit"

Refs are keyed on the underlying DOM node, not on position in a freshly-taken tree, so a ref stays valid across re-snapshots as long as the element is still alive — even across separate CLI invocations. A stale ref (page navigated since) raises a clear error instead of silently acting on the wrong element.

Token budget by defaultEvery snapshot caps at 150 elements with an explicit truncation notice, and --interactive filters to only actionable elements — nameless links/buttons and closed native <select> options are excluded, since neither is something an agent can usefully act on by reference. Use --diff to see only what changed since the last snapshot, and --within <ref> to scope to a region instead of the whole page.

Recipe format

A recipe is plain, readable JSON — not a black box. Review it with recipes recipe show before it ever runs against a real account.

// balance-check.json
{
  "site": "example.com",
  "start_url": "https://example.com/account",
  "ttl": "6h",              // stale past this → refuses to run
  "auth_binding": "browser-session",
  "steps": [
    {
      "mode": "fetch",
      "call": "GET /api/balance",
      "expect": { "status": 200, "json.currency": "USD" }
    }
  ]
}

Every step's expect clause is checked on every run — an exact match by default, or a …Contains suffix for a substring match where the real value legitimately varies (a count, a name). A failed assertion stops the run immediately and reports exactly what didn't match.

In-page replay

A fetch-mode step replays by running fetch() inside the real browser tab, not from a separate HTTP client. This is not fingerprint spoofing — every request carries the browser's own, unmodified TLS/UA signature, because it is the browser.

Read this before pointing it at a real accountAutomating your own logged-in account is not automatically fine everywhere just because nothing is spoofed — plenty of sites' terms of service restrict automated access to your own account too (banking and ticketing platforms especially). Check a site's ToS before using this beyond low-stakes things.

fetch vs dom mode

Not every endpoint is fetch-replayable — some sites protect internal APIs with a rotating, per-request signed token that can't be captured once and reused. dom mode is the fallback: locate an element by role + name (stable across reruns, unlike a raw ref), then read, click, or fill it — the same trusted-input engine as the core loop, not a second implementation.

ModeWhenSpeed
fetchdefault whenever a matching endpoint was observed on the wirefastest — no DOM touched
domfallback for signed-token requests, or content that only exists in the rendered pageref-based interaction
standaloneonly where auth is provably not browser-boundoutside the browser entirely

Command reference

CommandWhat it does
recipes open <url> --session <s>Opens or reuses a tab bound to a session name. Starts Chrome automatically if needed.
recipes snapshot [--interactive] [--diff] [--within <ref>]Reads the page as labeled elements instead of a screenshot.
recipes click <ref> / recipes fill <ref> <text>Trusted-input interaction, not a synthetic JS event.
recipes needs-humanChecks for a login wall or bot challenge — never solved automatically.
recipes record <out> --duration <ms>Captures real XHR/Fetch traffic while you use the page.
recipes recipe from-network <capture> <out> --site <s>Generates a draft recipe from a capture — review before trusting it.
recipes recipe show <file>Human-readable dry-run of exactly what a recipe will do.
recipes recipe run <file> [--dry-run]Replays a recipe, verifying every assertion, failing loud on mismatch.
recipes recipe watch <file> [--interval <s>]Runs a recipe and reports only when the result actually changed — cron-friendly with no interval.

Every command supports --json for structured output. Full reference, written for an agent to load directly: SKILL.md.

MCP integration

The same engine is also exposed as 10 typed MCP tools — calling straight into the same code the CLI calls, not a second implementation.

claude mcp add recipes -- node /path/to/recipe/mcp/server.js

Everything the CLI can do — open, snapshot, click, fill, run and watch recipes — is available as a typed tool with a schema, for any MCP-aware agent.

Benchmarks

Measured live, on real pages, against a real installed market tool (@playwright/cli) — not simulated, not cited from elsewhere.

Tokens, identical page4,202 chars137,444 chars — ~33× more

The token gap isn't because the underlying accessibility walk collects less data — recipes' own uncapped element count on that page (2,149) is the same order of magnitude as the comparison tool's (2,022 lines). The difference is a default 150-element cap with an explicit truncation notice, plus a purpose-built interactive filter — neither of which the comparison tool offers by default.

Limitations

  • Canvas/WebGL apps (Figma, maps) have no useful accessibility tree — not a good fit for this tool.
  • Sites with no accessible labels ("div soup") produce technically-correct, practically-useless snapshots.
  • --diff tracks the accessibility tree's membership and content, not pure visual state — a native <select> toggling open won't show as a change, since its options were already in the tree.
  • macOS only, currently — Linux/Windows Chrome paths are unverified.
  • No automated browser-driven test suite yet — npm test covers the logic that doesn't need Chrome; everything else is verified through live testing (see the build log).
