Also tested — not included as a clean number The same two tools on a GitHub repository README page came out roughly tied (9,393 vs 9,671 chars) — but recipes was logged into a real account in that test and claude-in-chrome's tab wasn't, so the extra authenticated-only UI (notifications, Copilot chat, user menu) isn't a fair delta either way. Pushed further — two real fixes, one honest mixed resultmeasured

Asked to make this decisively better, not just tied. Found and fixed two more real gaps — but a genuine multi-step round-trip test came out mixed, not a clean sweep, and that's reported as found rather than reworked into a win.

  • Fixed: nameless links/buttons (~10% of a typical page) dropped from --interactive — unidentifiable by a screen reader too, pure noise.
  • Fixed, bigger: a closed native <select> was exposing all its options — Wikipedia's language picker alone added 77 elements to every snapshot, before it was ever opened, and a closed option isn't even targetable by a trusted click anyway.
  • Reported as-is: a real "read → click → read again" round trip came out narrowly worse for recipes before the option fix (8,556 vs claude-in-chrome's 7,997 bytes) — and a clean re-test afterward hit a different real confound: recipes' shared persistent Chrome profile carried over Wikipedia's own saved UI state from the earlier click. That's a genuine tradeoff of staying logged in across commands, not a bug, but it makes this specific benchmark hard to run twice cleanly.

The honest caveat, stated plainly This is not "our engine collects less data" — recipes' own uncapped element count on this page (2,149) is in the same ballpark as theirs (2,022 lines). The real difference is that recipes ships a default 150-element cap with an explicit truncation notice, and a purpose-built role-based interactive filter; @playwright/cli, aimed more at test authoring and codegen than agent token budgets, offers neither by default (only an uncapped --depth option). That's a genuine, structural product difference — not a rigged test — but it's worth naming precisely rather than implying our raw accessibility walk is smaller, which it isn't.
Cited — not measured in this session An independent benchmark of Playwright MCP (a comparable snapshot-based tool) found ~114K tokens for a full browser-automation task via screenshots/verbose snapshots vs. ~27K tokens via a CLI-style flow — a ~4.2× reduction, consistent in direction and rough magnitude with what's measured above, on a different task and toolchain.
