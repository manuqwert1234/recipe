01 The problem

Screenshots don't fail — they lie

Today an agent drives a site by taking a screenshot, guessing pixel coordinates, and clicking. The failure mode isn't that this is slow. It's that click(847, 312) always succeeds — whether or not it hit anything — so a wrong click looks identical to a right one until three steps later.

The fix generalizes further than swapping pixels for an accessibility tree: even a resolved ref and a 200 response can both report success while the actual state change never happened. That principle — verify the outcome, not just the action — runs through the whole design and shows up again in §05.

02 Build decisions

What was considered, and why it lost

Three build-path proposals were argued in full before this one. Recording what lost — and exactly why — is what keeps them from being re-litigated later.

Which engine drives the browser

Rejected

Wrap vercel-labs/agent-browser

An existing CLI already does refs, sessions, and network capture. But its command surface is young and will churn — a bad foundation for something that touches logged-in accounts unattended.

Rejected

Fully standalone, raw CDP

Own every line, zero dependencies. Justified on paper by Page.createIsolatedWorld dodging page CSP — a justification that collapsed twice: Playwright ships bypassCSP: true outright, and replay is same-origin by definition, so CSP was never going to bite. What remained was "no install step," which doesn't buy months of rebuilt CDP plumbing.

Chosen

Own CLI, Playwright as a pinned library

A stable, versioned API from Microsoft — and what agent-browser itself runs on underneath. Full CDP access is still available via context.newCDPSession(page), so nothing is given up, only the obligation to maintain the plumbing. Everything that's actually new to this project — the recipe format, verification, in-page replay, the token-tuned snapshot engine — starts in week one instead of month three.

How state survives between CLI calls

Chosen

No daemon — Chrome holds the state

A CLI process exits in milliseconds; a naive design needs a background daemon to keep a tab alive between calls, and daemon lifecycle bugs are where tools in this category actually die. Playwright's connectOverCDP removes the need entirely: Chrome is started once and stays running: each invocation reconnects, resolves its tab from a small sessions.json keyed by CDP targetId, acts, and disconnects. No socket, no orphaned process, no lifecycle to get wrong.

Which browser, and how it's reached

Chosen

Your installed Chrome, dedicated persistent profile

Chrome 136+ ignores --remote-debugging-port against the default profile directory — verified against Chrome 151 on this machine. So Chrome is launched with channel: 'chrome' (your real binary, no 300 MB Chromium download) against a dedicated profile at ~/.web/profile. You log into each site once; cookies persist indefinitely after that. Real Chrome means a real TLS fingerprint and UA — which is the entire premise of §03.

On Cloudflare, explicitly When a Turnstile challenge appears, the tool surfaces needs-human rather than attempting it. You click once, in a visible window; clearance then persists for the Challenge Passage. Input is dispatched as trusted CDP events, never a synthetic .click() — challenge widgets specifically require a trusted event. No fingerprint spoofing, no UA forgery, no CAPTCHA-solving service, anywhere in this design.

The trap: two APIs that look interchangeable and aren't

Banned

page.request

Playwright's APIRequestContext shares the page's cookies — which makes it look like the right tool for a fast replay. It isn't: it sends from Node's http/https modules, not the browser's TLS stack. It would fail on Cloudflare exactly like a standalone client, for the exact same reason.

Required

page.evaluate(() => fetch(...))

Runs inside the page's own JavaScript context. Same TLS handshake, same UA, same cookie jar, same IP as the browser that's already logged in. This is the only replay path that inherits the site's trust in the session rather than merely its cookies. Encoded as a lint rule in the codebase, and proved empirically in §09 before any engine code is written.

03 The wedge

Why this and not a generated API client

Vercel's own agent-browser skills get derive-client already records a HAR and generates a standalone API client for a site — one that, in its own documentation, "skips the browser entirely." That phrase is where this project's whole reason to exist lives.

Positioning, stated plainly: this is derive-client for the sites where leaving the browser breaks the very auth you're trying to replay. Not a competitor — a recipe prefers a standalone call wherever one genuinely still works.

04 Architecture

One reconnecting CLI, one long-lived Chrome

No server process of ours runs continuously. The only long-lived thing is Chrome itself.

Each step in a recipe is tagged with one of three replay modes, chosen at record time:

modewhenspeed
fetchdefault whenever a matching endpoint was observed on the wirefastest — no DOM touched
domfallback for JS-signed / WASM-token requests, canvas appsref-based interaction
standaloneonly where auth is provably not browser-boundoutside the browser entirely

An assertion failure at replay time demotes a step to dom and re-records — the tool never guesses its way past a broken assumption.

05 Recipe format

A document you can read before it runs

A recipe is plain, diffable, git-trackable JSON — not a vendor cache living on someone else's server. recipes show renders it as a plain-language dry-run before anything touches a real account. The format is the product.

// recipes/portal-check-balance.json — annotated
{
  "site": "myportal.example.com",
  "ttl": "6h",               // stale past this → re-record before trusting it
  "steps": [
    {
      "mode": "fetch",       // in-page, same-origin — see §03
      "call": "GET /api/account/balance",
      "expect": {                // v1: response predicates only
        "status": 200,
        "json.currency": "USD"
      }
    }
  ],
  "auth_binding": "browser-session"  // not portable — needs a live login
}

What it stores: request shape (method, URL template, parameterized body/headers), step order, and expectations. What it never stores: credentials or a copy of the session — auth is ambient, inherited from whatever browser is live when the recipe runs.

That has one consequence worth stating without hedging: a recipe is portable as a document, not as an executable. You can read, review, diff, and share the JSON anywhere — that's the audit story, and it holds completely. Running it still requires a machine with a live, authenticated session for that site. It's a reviewable script, not a credential bundle.

Verification is scoped deliberately narrow for v1: expect covers status codes and JSON shape/value matches on fetch-mode steps only. Diffing a post-action accessibility snapshot to confirm "the right thing visibly happened" is a harder problem than the one this project set out to solve — it's punted, not forgotten.

06 Build phases

In order, each gating the next

Phase 0 exists to kill the project fast if the core claim doesn't hold. Everything after it only gets built once 0 has passed.

0

Preconditions

Prove — not assume — that in-page fetch() returns usable JSON with the browser's real TLS fingerprint; that it beats a Cloudflare challenge a Node-side copy of the same cookies does not; and that a triggering XHR is actually identifiable in real network noise (prefetches, analytics, debounced requests).

GateIf the Cloudflare claim fails here, the whole project is invalid — found in days, not months.

1

Chrome bootstrap + sessions

recipes browser start, persistent profile, connectOverCDP reconnect, sessions.json, needs-human detection.

2

Snapshot + refs

Accessibility tree via newCDPSession; refs keyed on backendNodeId so they survive re-snapshots. Then --diff, --interactive, --within, batching.

Done meansa 20-step task stays under ≈15K tokens.

3

Recipe format + show

The schema and the dry-run renderer — cheap to build, demoable in a day, and it is the trust story described in §05.

4

record

Capture Network.* to HAR with bodies; correlate wire traffic to user actions; parameterize by diffing two recordings of the same flow.

5

run + verification

In-page fetch() replay; the assertion engine; automatic demotion to dom mode and re-recording on any mismatch.

6

watch

Cron hook, session-expiry detection that fails loud instead of hanging, change diffing, notification.

7

Surfaces

A SKILL.md for Claude Code, and an optional ~150-line MCP wrapper over the same reconnect logic for other agents that want typed tools.

09 Verification & benchmark

How we'll know it works — and prove it publicly

  • Phase 0 gates, run in order, before any engine code.
  • Refs survive a React re-render; diffs stay correct on a mutating DOM.
  • An unseen site, cold: snapshot, fill a search box, submit, extract JSON — zero screenshots taken.
  • A 20-step task instrumented and checked against the ≈15K-token target.
  • A flow broken on purpose (renamed label, silently-rejected form) fails loudly — never reports false success.
  • Run under cron across a session expiry: clean needs-human, not a hang or a silent no-op.
  • The whole flow driven from bash with --json | jq, no Claude involved.

The launch asset: one real multi-step flow on a Cloudflare-protected site, run four ways — a cold LLM screenshot run, dom replay, in-page fetch replay, and derive-client's standalone client on the same site. Wall-clock and tokens for all four. That fourth column, showing the standalone client failing where ours doesn't, is the argument, and nobody has published it yet.

10 Known limits

Stated now, not discovered later

  • Canvas/WebGL apps (Figma, maps) have no useful accessibility tree — falls back to a screenshot and says so, rather than pretending.
  • Unlabeled markup ("div soup") produces snapshots that are technically correct and practically useless.
  • JS-signed, HMAC, or WASM-derived request tokens can't be fetch-replayed — those steps stay dom-only. — predicted correctly; hit for real on GitHub's rotating X-Fetch-Nonce, see §11
  • Write endpoints behind Turnstile pre-clearance may still re-challenge even when reads replay cleanly.
  • The Accessibility CDP domain is experimental — kept behind an adapter rather than called directly.
  • The logged-in Cloudflare case is proven only for a public, no-account test site so far; the authenticated case needs a real target chosen before it's confirmed. — closed with a real human click, see §11; the finding is more nuanced than assumed here
  • Pinned to one version of Playwright's API — an upgrade needs a smoke test, not a blind bump.
  • No automated test suite — everything verified was live, ad-hoc testing against real sites, not a re-runnable suite.
  • Chrome must be kept running manually — the no-daemon design means nothing restarts it after a reboot or manual quit, which matters once a cron entry depends on it (see §11).

11 Built — what reality changed

Every predicted risk that actually happened, plus what wasn't

This was fully built and run against real sites, including a real logged-in GitHub account and a real cron schedule. Some of §10's predictions landed exactly; some of what broke wasn't predicted at all.

The Cloudflare finding — closed, but narrower than assumed

A real Turnstile was cleared by hand, confirmed via the actual cf_clearance cookie. But both in-page fetch() and the banned standalone page.request then returned 200 with that cookie — Cloudflare didn't re-check the TLS fingerprint on the follow-up request. The TLS divergence (§03) is real and measured; its payoff concentrates in obtaining clearance, not necessarily in every request after. In-page replay stays strictly safer — just not proven necessary post-clearance on the two real sites tested.

Two bugs the design didn't anticipate

Zero-tab crash

Playwright's connectOverCDP throws outright with no open tabs — it needs an existing target to attach its default context to. Fixed by guaranteeing a tab exists via the raw CDP HTTP endpoint before Playwright ever connects.

needs-human false positive

Matched CSS class fragments that persist whether the widget was solved or not. Fixed: those markers now also require the clearance cookie to be absent.

Recipes assumed things they shouldn't have

No starting page

A hand-written recipe implicitly assumed its session's tab was already on the right page — broke the moment that tab navigated elsewhere. Fixed with an optional start_url the runner navigates to first.

Format fields that were documentation only

ttl and auth_binding were printed by show but never checked by run. Both are real now: a stale recipe refuses to run; auth_binding: "none" genuinely omits credentials.

The Phase 4 gap got filled: record used to dump raw traffic a human read to hand-write a recipe. recipe from-network now generates a draft automatically — proven end to end on real GitHub traffic.

Shipped beyond the original plan: dom mode was scoped as "only if needed" — it turned out to be needed for replay itself. GitHub's internal API requires a rotating, single-use nonce per request; reading it once and reusing it still gets rejected. dom mode's read/click/fill route through the same trusted-CDP-input engine from §04 — not a second implementation — and all three are proven against the real account.
